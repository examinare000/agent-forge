# Deep Reasoning（深い推論の手続き）

難しい判断を「暗黙の思考力」に頼らず、明示的な手順で再現するための足場。
正本トリガは `~/.claude/rules/93-deep-reasoning-protocol.md`、発火閾値の正本は `~/.claude/rules/02-model-fallback-matrix.md`、構えの選択は `~/.claude/rules/05-stance-and-triggers.md`。

各ステップは **前提 ➔ 目的 ➔ 行動 ➔ 想定される結果** の連鎖（`~/.claude/rules/00-core-principles.md`）の明示化である: 目的 = Step 1、前提 = Step 2、行動 = Step 3〜4、想定される結果 = Step 5〜6。

## 発火条件（自己判定チェックリスト）

以下のうち **1 つ以上**該当したら本手続きを必ず実行する（= 非自明タスク全て。**全メイン共通で 1 項目以上**。正本: `~/.claude/rules/02-model-fallback-matrix.md`）。
ユーザーの明示指示（「深く考えて」「熟考して」等）は**チェックリストによらず単独で即時発火**する（93 トリガ (b)）。

- [ ] 影響ファイルが 3 つ以上
- [ ] アーキテクチャ・データモデル・公開 API に関する決定を含む
- [ ] 非可逆操作を含む（migration・削除・リリース・外部公開）
- [ ] 要求に 2 通り以上の解釈がある
- [ ] 直前の試行（修正・実装）が失敗した
- [ ] セキュリティ・認証・課金に関わる
- [ ] ユーザーが「設計して」「どう思う」「難しい」と発話した

## 手順（順序固定・省略禁止）

各ステップの成果物は**応答内に見出し付きブロックで出力**する（ファイルは作らない）。
ステップを飛ばさない。埋められない欄は捏造せず「未検証」と書く。

### Step 1: 問題再述
- 要求を**自分の言葉で3文以内**に再述し、成功条件を1文で書く。
- 再述に自信が持てない（解釈が割れる）場合は、ここで停止してユーザーに確認する。

### Step 2: 前提台帳
判断の土台となる前提を表に列挙する。

| 前提 | 根拠（path:line / ユーザー発言 / URL / consult回答（引用付き）） | 状態 | 崩れた時の影響 |
|---|---|---|---|
| 例: 認証は JWT 前提 | `src/auth/jwt.ts:12` | 検証済 | 大 |

- 状態は `検証済` / `未検証` の二値。根拠欄が埋まらない前提は必ず `未検証`。
- **二次情報（エージェント報告・表示シグナル・過去ログ・記憶・慣習）のみを根拠とする前提は `検証済` にしない**。`検証済` は一次情報（実ファイルの Read / grep・実行コマンドの出力・原文書の該当箇所）との照合を要する。
- **「影響: 大 × 未検証」が残る場合は先に検証する**か、確認不能ならユーザーに質問する。コード外の知識（設計原則・外部仕様・一般知識）の照会と裏取りは `references/external-knowledge.md` に従う。

### Step 3: 仮説 → 証拠 → 反証
- 採用候補の方針を1つ立て、支持する証拠を列挙する。
- その後、**反証探索を必ず行う**: 「この方針が間違っているとしたら最強の論拠は何か」を最低1つ明示する。
  反例 grep・エッジケース・既存パターンとの衝突を**能動的に**探す。「反証は見つからなかった（探した箇所: …）」も可、探さないのは不可。

### Step 4: 代替案
- コミット前に**最低2つ**の代替案を「1行トレードオフ + 棄却理由」付きで提示する。
- 代替案が本命より優れていると気づいたら、素直に乗り換える。
- 棄却した代替案は、本ステップの出力ブロックに棄却理由とともに残す。**その内容をオーケストレーターが `docs/trial-log/` へ転記する**（`~/.claude/rules/94-self-improvement-protocol.md` (t2)。形式は `~/.claude/rules/30-documentation-management.md`）。後続セッションが同じ案を再検討する無駄を防ぐため。本手続き自体はファイルを作らない。

### Step 5: プレモーテム
- 「この方針で進めて**失敗した**と仮定する。最も可能性の高い原因は何か」を3つ挙げる。
- 各原因に検知方法（どのテスト・ログ・レビューで気づけるか）と緩和策を1行ずつ添える。

### Step 6: コミット判定
- 確定前に自問する: 「この行動の想定される結果は、Step 1 の目的と Step 2 の前提に反していないか」。
  反していれば Step 3 に戻るか、情報収集を深めて新たな選択肢を考案する。
- 確信度を `高` / `中` / `低` で自己申告する。
- `低`、または「影響: 大 × 未検証」の前提が残る場合は、`03-agent-behavior.md` のエスカレーション・停止規律に従い**進めずに質問**する。
- `高` / `中` なら方針を確定し、以降は通常の開発サイクル（TDD・レビュー）へ。

## 運用上の注意

- 本手順は思考の足場であり、表を埋めること自体が目的ではない。「明らかなので省略」は不可。
- 捏造禁止: 根拠のない前提・存在確認していない API 名・実行していない検証結果を「検証済」と書かない。簡潔さより判断の透明性を優先する。

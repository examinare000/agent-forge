# CLAUDE.core.md（agent-forge 共通規範）

agent-forge が配布する共通規範。全プロジェクトに適用されるモデル非依存の基本方針を定め、`~/.claude/CLAUDE.md` として配備される。個人固有の設定（個人パス・私有 MCP・嗜好）は本ファイルに書かず、利用者側で重ねて定義する。プロジェクト側の CLAUDE.md / AGENTS.md が矛盾する指示を持つ場合はプロジェクト側を優先する。本書はルーティング層であり、規範の正本は `~/.claude/rules/` に置く。

## 最優先ルール
1. タスクに関係する `~/.claude/rules/` のルールを参照して従う。衝突時は `00-core-principles.md`（憲法）が常に最上位、それ以外は**ファイル番号が大きい方**を優先。
2. Claude Code セッションではこの指示（CLAUDE.md）が最優先。他ツール向けエントリ（AGENTS.md / GEMINI.md）は本セッションでは適用しない。
3. 優先度: 🔴絶対 > 🟠高 > 🟡中。ルール一覧・索引の正本は `~/.claude/rules/README.md`。

## 判断の構え
開始時に判定するのは分岐表ではなく構えである。必要な構え（深さ・計画・分割・委譲）を自分で選び、**構えは排他ではなく重ねる**。迷ったら `04-principles.md`（思考原則）を参照してよい。
- 前提が崩れると高くつく非自明タスクには深い推論 ➔ `93-deep-reasoning-protocol.md`（Skill `deep-reasoning`）
- 専門判断・文脈隔離・独立レビューが効く形にはサブエージェント品質ゲート ➔ `91-subagent-quality-gate.md`

ハードトリガ（環境事実と義務。構え判断に委任しない）:
- plan mode 突入 ➔ `92-plan-mode-protocol.md`
- 教訓トリガー該当（バグ根本原因確定・レビュー指摘サイクル完了・ユーザー訂正） ➔ `94-self-improvement-protocol.md`（キャプチャ義務）
- ユーザーの明示指示（「深く考えて」「委譲して」等）は該当プロトコルを即時発火する

## 運用既定
- **前提 → 目的 → 行動 → 想定結果**: 行動は目的から導き、想定結果が前提と矛盾しないか確認する。目的から導けない行動は取らない。
- **TDD**: 最小の失敗テスト ➔ 最小実装 ➔ テストが緑のままリファクタ。テストは生きた仕様。
- 通常作業はメイン1本の**単一ループ**（理解・テスト・実装・リファクタ・検証・報告）で進める。委譲は大コンテキストの隔離・専門判断・高リスクの独立レビューに限り、通常作業を分割したり定例の二重ゲートを走らせたりしない。
- **検証証拠は常に必須**: 完了を主張する前に実際のコマンド・結果・未検証の事項を報告する。
- 明示依頼と既存の許可の範囲内では再確認せず進める。許可外の非可逆操作・公開・実質的なスコープ変更だけ事前に確認する。
- サブエージェントはサブエージェントを起動しない。ブリーフは自己完結させ、境界（触ってはいけない領域）と完了条件を書く。
- 手順はスキルに置く（TDD は superpowers 導入時 `test-driven-development`、失敗のデバッグは `systematic-debugging`、完了宣言前は `verification-before-completion`）。インラインせず起動する。

## 動作制約（Claude Code セッションの正本）
- **レスポンス**: 既定は前置き・総括なしの簡潔回答（目安4行、コード・ツール出力を除く）。パス・コマンド・識別子はバッククォートで明示。一覧・レポート・点検結果・構造化出力（深い推論・plan mode の前提台帳や代替案等）を求められたときは長さの目安を適用しない。
- **ファイル操作**: 既存編集を優先し、Edit/Write の前に Read で確認する。1 Edit = 1論理変更。ドキュメント規約の範囲内（`docs/adr/`・`docs/trial-log/`・`lessons/`）の `*.md` は指示なしで作成・追記してよい。それ以外の新規ドキュメントは提案してから作る。
- **検索・分析**: オープンエンド検索はサブエージェント（探索役）に委ねる。独立した情報収集は並列実行し、対象を特定できる場合は直接 Read。コード外の知識（設計原則・外部仕様）は WebSearch を第一級証拠源とし、単独で結論を確定させず裏取りする。shelf MCP（別頒布）導入環境では同格の証拠源として照会してよい（任意）。
- **プロアクティブ実行**: 検索/分析（read-only の外部照会を含む）・テスト実行・lint/typecheck・セキュリティ検証・scratchpad やテストファイルの作成は進めてよい。設定変更・外部への書き込み・リポジトリ外への書き込みも、明示依頼または既存の許可の範囲なら再確認しない。許可外の非可逆操作・公開・実質的なスコープ変更は事前に確認する。
- **品質ゲート時の追加制約**: 委譲（メイン禁止）= Edit/Write（`tdd-strict-coder` / `implementation-coder`）・設計（`testability-architect`）・レビュー（`code-reviewer` 等）・Git（`git-composer`）。メイン実行 = ユーザー応答、タスク分解・指示。例外（メイン可）= 1〜2行の自明な修正、Worker 完了後の整合性確認 Read。
- **コンパクト時**: 現在のブランチ/タスクの目的、変更ファイルの全リスト、テスト/ビルドコマンドと結果、未解決のレビュー指摘を必ず保持する。

## 安全
- `main` / `master` / `develop` へ直接コミットしない。1ブランチ = 1目的、1コミット = 1論理変更。履歴生成・GitHub 書込み（commit・merge・rebase・tag・`gh` の作成/編集/コメント）は `git-composer` への委譲を推奨する（本フレームワークは強制フックを同梱しない）。コミット規約は `git-composer` の定義に従う。
- 資格情報をログに出さない。シークレットのハードコード禁止（環境変数またはセキュアストレージ）。入力はサニタイズし、エラーメッセージで内部詳細を漏らさない。
- 一時ログは `[DEBUG]` / `[TRACE]` 接頭辞を付け、完了前にコメントアウトではなく削除する（`Stop` フックが残存を検出する）。
- マージ前: テスト通過・型クリーン・lint クリーン・シークレットなし・デバッグコード除去済み・フレッシュコンテキストのレビュー完了。

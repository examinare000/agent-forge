# 95. オーケストレーション委譲プロトコル（メインセッション = オーケストレーター）

メインセッションがサブエージェントへ委譲する時の運用の**正本**。通常作業はメインの single-loop（理解 → テスト → 実装 → リファクタ → 検証 → 報告）で行ってよく、委譲は大コンテキスト隔離・専門判断・明示的な高リスク独立レビューが効く時に選ぶ（「委譲コストの下限」参照）。
provider の入口で Main をオーケストレーターとする分担が指定されている場合は、その分担を優先する。全体判断と小タスクへの分解は Main、境界が確定した実行は SubAgent が担い、委譲コストの下限以下の作業は Main でよい。
**メインセッションを担う provider は固定しない**。本ファイルの規範文には provider 固有の機構名・コマンド名を書かず、現行環境の実体は各 provider の入口の固有節と `~/.claude/reference/delegation-routes.md` が持つ。
委譲先は**論理ロールID**（9つの論理ロール。同梱エージェントとの対応は末尾の表）で指名する。品質ゲート・多数決の詳細は `91-subagent-quality-gate.md` が正本。変更系 git/gh は `git-compose` ロールへ委譲する。

## 委譲の規律

- **ネスト禁止**: サブエージェントはサブエージェントを起動しない。オーケストレーションの所有者はメインセッションのみ。
- **最小タスク単位**: 委譲前に、独立に検証可能な最小単位（1タスク = 1関心事）へ分解する。
- **自己完結ブリーフ**: ワーカーはセッション履歴を継承せず計画ファイルも読まない前提で、次を必ずインライン展開する（「必要十分」であって「最小」ではない — 痩せたブリーフは `NEEDS_CONTEXT` の往復を買う）:
  - ゴール / 対象ファイル / **明示的な境界（触ってはならないファイル・領域）** / 制約 / 決定済み事項
  - 完了条件 = **成果物の型に一致した検証コマンド**（削除なら残存列挙 0 件、抽出・移植なら移植先の実在と内容確認など）
  - 前提も判定式（コマンド + 期待値）で書く。判定式にできない前提は「未検証:」を冠し、探索を打ち切る根拠に使わせない（断定形で渡された前提は受け手にとって閉じた事実になる）
  - 実装・調査の委譲では、対象リポジトリの `docs/trial-log/` に関係するファイルがあれば着手前に読む指示（マルチリポでは `web/docs/trial-log/` のように作業対象リポのパスへ解決する）
  - **判断範囲を閉じる指示**（必須）: 判断が要る点は推測で埋めず、該当箇所を未変更のまま `NEEDS_DECISION`（質問 + 選択肢 + 推奨）で返す（`03-agent-behavior.md`「判断停滞のエスカレーション」）。native subagent 機構を持つ provider では既存の契約・パターン内で取り消せる局所判断を委譲範囲に含めてよく、要件・公開契約・スコープ・未許可の非可逆操作に関わる判断だけを Main へ返す。
- **独立レビューの文脈**: 実装者の推論履歴や他票の結論を継承させず、依頼原文・確定した制約・検証対象・一次情報の所在を渡す。履歴非継承が実現できない経路では独立票と数えない。起動方法の正本は `~/.claude/reference/delegation-routes.md`。
- **委譲の粒度はワーカーのターン予算に合わせる**: 1 ブリーフは「読む・編集する・検証する」を `maxTurns` 内で 1 往復できる粒度（目安: 対象 1 モジュール・Red 1 回・Green 1 回）に切り、収まらない作業は起動**前**に分割する。上限で停止したワーカーの返答は完了でも `BLOCKED` でもなく**無印の中途状態**であり、「続行」を送る前に成果物の実体を測ってから、再開・引き取り・再分割を選ぶ。**判定行（PASS/REJECT）に到達しないレビュー出力は判定不成立**。調査・レビュー系ブリーフは読む対象を**ファイル列挙で閉じ**、件数計測はスクリプトとして渡す（詳細は `~/.claude/reference/delegation-routes.md`）。
- **汎用資産の手続きはローカル強制と衝突する前提で起動する**: プラグイン提供スキル・ユーザースコープのエージェント定義・自作スキルは、当該リポジトリのフック・権限設定・起動時制約を知らない。起動**前**に、その手続きが要求する (a) **実行主体**（変更系 git/gh はメインで実行できない ➔ `git-compose` へ）と (b) **記録経路**（trial-log の自書きが不可なら「報告 ➔ メインが転記」へ）を解決し、ブリーフに明示する。
- **労力スケーリング**: 単純な調査 = エージェント1体 / ツール呼び出し3〜10回、比較 = 2〜4体、複雑な網羅 = それ以上。読み取りは並列化し、書き込みは直列化する（1ツリーに書き手は1人。境界が非重複なら並列書き込みも可）。
- **ワーカー出力契約**: ワーカーは凝縮した結果（約1〜2Kトークン: 結論 + `path:line` 形式の根拠ポインタ）を返す。生トランスクリプトやファイルダンプは返さない。加えて、試した経路ごとに「目的 / **前提（出発点の状態と置いた仮定。不確かなものは「未検証:」と明示）** / やったこと / 結果（採否と、採らなかった理由） / 残課題」を各1文と、記録した `docs/trial-log/<ファイル>.md` のエントリのポインタを返す（試行が無ければ「なし」と明記。**前提は試行した本人しか持たない情報なので、ワーカーが書かなければ永久に失われる**）。ゲート実行を委譲した場合は最終判定行だけでなく **exit code と各段の実行証跡**を返す。条件付き通過・持ち越しを返すロールは、条件ごとに**解消コマンドと、その出力が残るパス**を明記する。オーケストレータは、受領した根拠のうち結論の土台となる件数を転記前に同じコマンドで 1 回再計測する。

## 委譲先の選定（ベンダー特性ルーティング）

**選定原則**（`04-principles.md`「委譲と構えの選択」）: 判断を含む役割は安い層に置かない。読み取りが重い作業はメイン文脈に載せない。迷ったら安い方を先に投げ、失敗を観測してから引き上げる。非可逆な領域ではコスト最適化しない。原則で決めきれない時、以下の 3 段階手続きと表が決定手続きの正本。能力ティア（A/B/C）の正本は `02-model-fallback-matrix.md`。

**第1段: 足切り（能力ティア）** — 判断を含む役割（設計・タスク分解・レビュー・完了判定・敵対的検証）に Tier C 相当を割り当てない。別ベンダーの委譲先は、ツール名ではなく解決後の (model, effort) のティアで判定する。native subagent 機構を持つ別ベンダー provider の単純実行・許可済み Git・中継・限定設計補助には 許可範囲は `02-model-fallback-matrix.md`「Codex 側のモデル解決」のモデル・effort 解決規則に従い、役割は以下の一般表で選ぶ。

**第2段: タスク形状 → 既定の委譲先**

| タスク形状 | 既定の委譲先 | 選定根拠（特性） | 代替 |
|---|---|---|---|
| 仕様固定の忠実実装・機械的置換・定型リファクタ | `faithful-implementation` ロール（Tier B 相当以上） | 要件と受入条件が確定済み。native subagent 機構を持つ provider では既存パターン内の可逆な局所判断を許可し、他の実行経路はその役割定義に従う | 原因調査・振る舞いの解明が必要なら `tdd-implementation` へ引き上げ |
| TDD 実装・バグ修正（実装レベルの判断を含む） | `tdd-implementation` ロール（Tier B 相当） | Red-Green-Refactor の規律遵守と中コストの両立 | 別ベンダーの実装役（行き詰まり時） |
| 長時間の自律実装・行き詰まりの突破・独立した第2実装 | 別ベンダーの実装役（自分以外の provider。Tier B 相当以上） | 別系統の推論による脱出力。**非対話**の委譲先では判断事項をブリーフで事前解決し、提案のみの時は読み取り専用を明記する | 競合提案（Skill `dual-track-proposals`） |
| 大コンテキスト読解（大量ログ・巨大ファイル・全文横断）、Web 接地調査、第2意見 | 大コンテキスト・検索接地に強いベンダーの委譲役 | メインの文脈を汚さず結論だけ受け取れる | 探索役 |
| リポ内探索・所在特定（結論だけ要る） | 探索役（読み捨て文脈の探索エージェント） / Tier C 相当 | 読み捨て文脈で広く探索し、ファイルダンプを返さない | — |
| 設計・タスク分解・境界設計 | `architecture` ロール（Tier A） | 判断役。Tier C 禁止 | 別ベンダーの `architecture` ロール（Tier A 相当かつ effort xhigh） |
| 検証・レビュー | 実行は `test-execution` ロール（安価）／判定は `code-review` ロール（Tier B 以上）／推論成果物は `adversarial-review` ロール（Tier A） | 「実行は安く、判定は上位に」の非対称配置 | 別ベンダーの同ロール（effort 下限は `02-model-fallback-matrix.md`） |
| 票が割れた時の第3票 | **メインを担っている provider 以外**のベンダー | 相関バイアス回避（正本: `91-subagent-quality-gate.md`）。起動前に投じるロールの判定ティアと effort 下限を満たすことを確認 | — |

**タイブレーク**（複数行に該当する時）: 大コンテキスト読解 vs 探索役は「読む対象がメイン文脈に載るか」／忠実実装 vs TDD 実装は「要件と受入条件が固定済みか、原因調査・振る舞いの解明が必要か」（両者とも振る舞いの変更には TDD を適用する）／第2実装 vs 競合提案は「方針が確定しているか」（未確定のまま別ベンダーに書かせない）。詳細は `~/.claude/reference/delegation-routes.md`。

**可用性のフォールバック**: 別ベンダーの委譲役・上位互換エージェントは環境に存在しない場合がある。存在しない委譲先が既定の行は「代替」列（無ければ実装ロール / 探索役）へフォールバックする。

**第3段: トークン効率の規律**
- **読み取りが重い作業をメイン文脈で実行しない**。使い捨て文脈（探索役 / Tier C / 大コンテキスト委譲役）へ出し、凝縮結果のみ受け取る。
- **同一ブリーフの複数ベンダー並行投入は、競合提案と第3票に限る**。常用は純粋な重複コスト。
- **委譲コストの下限**: およそ5行以下の編集、ツール呼び出し1〜2回で済む調査は、委譲せずメインで実行する。
- **精度優先の例外**: 非可逆操作・公開 API・データモデルに触れるタスクは、安い委譲先を選ばない。


**選定を外した場合**: 委譲先を選び直した事実と理由を `docs/trial-log/` に記録する（`94-self-improvement-protocol.md` の (t4)）。本表はこのフィードバックで改訂する。

## 質問返しプロトコル（continuation-first）

- ワーカーは委譲された判断範囲を超える箇所を未変更で `NEEDS_DECISION`（具体的な質問 + 選択肢 + 自身の推奨）として返す。native subagent 機構を持つ provider の局所判断の許可は「委譲の規律」に従う。Main は依頼と既存許可から決まる判断を解決し、未許可の非可逆操作・外部公開・実質的なスコープ変更だけユーザーへ上げる（`03-agent-behavior.md`「判断停滞のエスカレーション」）。
- 回答は **SendMessage で同一エージェントへ**返し、部分成果を生かす。エージェントのコンテキストが壊れている場合のみ新規再委譲する。
- 非対話の実行経路では判断事項をブリーフで事前解決し、必要なら再開機構に回答を載せる。provider 名だけで非対話と判定しない。メッセージを受け取れる native agent には同じ agent へ回答して継続する。
- `BLOCKED` / `DONE_WITH_CONCERNS` は進行前に評価する: 前提を直す / タスクを分割する / ユーザーへエスカレーションする。
- この continuation-first 原則は、質問時に再委譲せよと書くスキル本文より優先する。

## 検証と並列化

- 完了基準コマンドはメインが自分で実行してよく、文脈隔離が要る時は `test-execution` ロールへ委譲する。高リスク差分のマージ前は `code-review` ロールを 1 回起動する。
- 独立タスクは並列起動する（並列起動機構を持つ provider では、1メッセージ内に複数のサブエージェント呼び出しを置く）。

## 特殊委譲

- **非自明な実装**（複数の妥当なアプローチ / 新規性のある設計面 / 過去に失敗した試み）→ 競合提案（Skill `dual-track-proposals`。落選案の記録義務は本ルール側でも担保する）: 別ベンダーの実装役 × Tier B 実装役の競合提案をオーケストレーターが採用または統合し、単一の実装者が適用する。**落選した提案と不採用の理由は `docs/trial-log/` に記録する**（`94-self-improvement-protocol.md` (t2)）。実装アプローチ水準のみが対象 — アーキテクチャ水準の設計は先に `architecture` ロールへ。
- 別ベンダー委譲の実体（経路・戻り後のゲート所有・ブリーフの書式）は `~/.claude/reference/delegation-routes.md`。

# 91. サブエージェント品質ゲート戦略
サブエージェントを Worker / Reviewer として起動し、品質を担保するための戦略。**provider 中立**であり、委譲先は**論理ロールID**（対応表は `95-orchestration-protocol.md`）で指名する。

本戦略は既定動作ではない。ユーザーの明示要求、または high-risk 条件（アーキテクチャ・セキュリティ・非可逆変更）で発動する明示モードであり、通常作業はメインセッションの single-loop（`95-orchestration-protocol.md`）で行い、routine double gate は行わない。

## 適用条件
**実装主体**は実装ロール（`tdd-implementation` / `faithful-implementation`）である。

## 品質ゲートの運用フロー
1. **Worker起動**: メインセッションが適切な論理ロールを、自 provider のサブエージェント起動機構で起動する（機構を持たない provider の代替は `05-stance-and-triggers.md`「機構非対応時の縮退」）。
2. **AIアンチパターン検査（本モード発動中は必須）**: Worker が実装差分を生成したら、完了宣言前に `ai-antipattern-review` ロール（手続きは `review-ai-antipattern` 手順書）を実行する。実行責任はオーケストレーター。本モードの外の single-loop 通常作業では任意（明示依頼時は実行）。
3. **品質判定**: Reviewer 系が `PASS` / `REJECT` を判定。antipattern の重大指摘も REJECT 扱い。
4. **ループ**: `REJECT` の場合は前段ステップへ戻り修正し、PASS を取得するまで完了としない（推論成果物のゲート `adversarial-review` も同じ）。**REJECT を受けて方針そのものを変更した場合**は、捨てた方針と棄却理由を `docs/trial-log/` に記録してから修正へ入る（`94-self-improvement-protocol.md` の (t3)。書き手は Write 権限を持つ実装ロールかメイン）。**REJECT ループの終了条件は PASS だけではない**:
   - **ゲート不成立**: 指摘の解消に必要な変更が fix ステップの作用域（当該ブランチの差分・書込可能パス）の外にある場合（gitignore 対象・symlink 先・別リポジトリの資産を検査するゲート等）は、修正対象ではなく検査母集団の欠陥であり、次ラウンドへ進まず停止して検査側の修正を提案する。
   - **緩和禁止**: ラウンド数や停滞を根拠にした条件付き通過・基準の緩和はしない。収束しないループは、指摘クラスの掃引（`03-agent-behavior.md`「掃引キー」）か第 3 票、またはユーザーへの停止報告で終える。**収束しないと判定する条件は `05-stance-and-triggers.md`「ハードトリガ」の判断停滞行**であり、該当したら次ラウンドへ進まず `03-agent-behavior.md`「判断停滞のエスカレーション」で上げる（掃引は合格基準が決まっている場合にだけ選ぶ）。
   - **持ち越しの成立条件**: 条件を後段へ持ち越す条件付き通過は、持ち越し先がその検証を実行する構造を持つことを持ち越し時に Read で確認して初めて成立する。構造的に実行しない段へ持ち越した条件は解消されず、その通過は**不成立**である。

## 敵対的検証（標準運用の品質ゲート）
メイン（標準運用ティア = S / A）の過信を検証側の厚みで**本モード発動中は**補正する（ティアと実モデルの対応は `02-model-fallback-matrix.md`）。

- **反証ファースト起動テンプレート**（Reviewer 系サブエージェント全般に前置き可能）:
  ```markdown
  あなたは検証者です。まず対象が**間違っている**という仮説で反証を3件試み、
  崩せなかった場合のみ PASS を出してください。根拠なき PASS は REJECT として扱われます。
  ```
- **多数決手順（正本）**: アーキテクチャ級判断（アーキテクチャ・データモデル・公開 API・非可逆操作・大規模リファクタ）では独立 2 票（`adversarial-review` ロール + `code-review` ロール）を取る。2 票一致で確定。**不一致時は第3票を、メインセッションを担っている provider 以外のベンダーから取る**（同系モデル同士の相関バイアスを避けるため。担い手は投じるロールの判定ティアと effort 下限を満たす実効モデルから選定する — `02-model-fallback-matrix.md`「クロスベンダーのティア対応」。呼び出し経路は各 provider のエントリ固有節）。
- 票は互いの結果を見せず**独立起動**する（並列起動機構があれば同一メッセージ内で）。本多数決は実装前ゲート最大 1 つの内部構成であり、ゲート件数の超過ではない。

## 注意事項
- **権限**: 破壊的なファイル削除はメインセッションまたは `git-compose` ロールのみ。
- **git/gh の委譲と多重起動禁止**: 正本は `95-orchestration-protocol.md`「委譲の規律」と `git-composer` 定義（履歴生成系はメインで実行せず `git-compose` へ 1 回の委譲にまとめる。`gh pr merge` はユーザー同意の上でメインが実行）。
- **フックは無効化も迂回もしない**: フックにブロックされたら、フックが用意した正規経路（`git-compose` ロールへの委譲等）へ切り替える。**正規経路以外の代替手段を発明・永続化しない** — ブロックの意図ごと迂回する回避策はガードを静かに無効化し、過剰ブロックほど迂回を誘発する。誤検知・不当なブロックも迂回しない。フック保守の明示依頼・既存許可があれば範囲内で検証を伴う修正を行い、許可がなければ停止して修正を提案する。
- **全経路が塞がれたら個別回避ではなく境界の設計欠陥として一件で報告する**: フックが指定した正規経路も同じ強制層群（sandbox / クラシファイア）に拒否されるなら、それは自分の操作の誤りではなく強制層の連言の解空間が空である状態で、どこにも FAIL が出ない。同型の拒否をコマンドごとの再試行・都度の特権昇格要求で処理せず、**塞がれた経路の集合**と**義務付けられている操作**を 1 通にまとめ、境界そのものの修正提案としてユーザーへ上げて停止する。

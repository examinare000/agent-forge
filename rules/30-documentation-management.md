# 30. ドキュメント管理

## ドキュメント形式ポリシー（正本の所在）🟠

判断軸は「**正本 vs 生成物**」と「**常時ロード vs オンデマンド**」。Markdown を単一正本とし、人間向け HTML は SSG（例: MkDocs）で生成する。

| 区分 | 正本（編集対象） | 役割 |
|------|------|------|
| 設計書・仕様書 | **Markdown**（`docs/design/*.md`） | AI が低トークンで読め、git 差分・レビューも軽い単一正本。図は **Mermaid**。HTML は `mkdocs build` で生成（手編集しない。`site/` はコミットしない）。`docs/design/app-ui.html` 等の手書きビジュアル正本は例外として残置 |
| ADR・要件・計画・運用 | **Markdown**（`docs/adr/`・`prd/`・`plan/`・`operations/`・`tech/`） | 意思決定・現在状態の **AI コンテキスト圧縮層** |
| 索引（段階的開示） | **Markdown**（`docs/README.md`・ルート `AGENTS.md`） | 「何を・いつ読むか」の索引。本体は必要時にオンデマンド取得 |

- **実装の正本はコード**: 設計書は責務・契約・意図の記述に徹し、実装コードは掲載しない。

## ディレクトリ構造
- `docs/README.md`: **ドキュメント索引**（段階的開示の入口）
- `docs/design/`: **設計書・仕様書の正本（Markdown）**。HTML は生成物
- `docs/prd/`: 要件定義 (PRD)
- `docs/adr/`: アーキテクチャ決定レコード (ADR)
- `docs/plan/`: 実装計画・タスク指示書（作業領域。完了後は恒久ドキュメントへ移し削除）
- `docs/trial-log/`: **試行ログ / 開発ノート**（開発中ずっと追記・更新する live-docs。ADR の補助ドキュメント）
- `docs/tech/`: 技術文書（DBスキーマ、API設計等）
- `docs/operations/`: 運用文書
- `docs/research-reports/`: 調査・評価レポート

## ドキュメント規約

### PRD
- **配置**: `docs/prd/<機能域>-<内容>.md`
- **構成案**: 概要（目的と背景） / 機能・非機能要件 / 受け入れ基準（条件・実行・結果）

### ADR
- **配置**: `docs/adr/<3桁連番>-<決定内容>.md`
- **ポリシー**: 既存ADRは変更せず、新ADRで上書き（ステータス: 採用済み / 廃止 / 検討中）
- **構成案**: 背景 / 検討した選択肢（メリット・デメリット） / 決定 / 理由 / 結果（影響）
- **trial-log との連携**: 「検討した選択肢」の各項目から、対応する試行の詳細を `docs/trial-log/<file>` の該当エントリへリンクする。ADR は決定の要約に徹し、過程は補助ドキュメント側に置く。

### 技術文書
- **配置**: `docs/tech/<分野>-<内容>.md`

### trial-log（試行ログ / 開発ノート）

**位置づけ**: 開発中ずっと追記・更新し続ける **live-docs**。ADR が「どう決めたか」を要約するのに対し、trial-log は「そこへ至る過程で何を試し、何が起きたか」を保持する。防ぐ対象は ①同一セッション内で同じミスを繰り返す ②作業の目的を見失う ③棄却した案を再試行・再提案する、の 3 つで、**読み返した瞬間に防がれる**ため「最後にまとめて書く」運用では価値が出ない。成功した試行の正本は ADR・設計書・コミットログにあるため再記述せず 1 行の参照に留める（蓄積されるのは失敗・棄却が中心になる）。
記録義務のトリガは `94-self-improvement-protocol.md`、**手続きと書式は Skill `trial-log`（`~/.claude/skills/trial-log/SKILL.md`）**が正本。本節は配置・単位・書き手・読む義務・ライフサイクルを定める。

- **配置と単位**: `docs/trial-log/<論点のスラッグ>.md`。**1 ファイル = 1 つの試行内容**（ブランチ単位ではない。読み手は「この論点で過去に何を試したか」で探す）。同じ論点のファイルがあれば追記、迷ったら追記（乱立より肥大の方が回復しやすい）。冒頭に範囲の 1 文を置く。
- **サブモジュール構成の場合**（親 + サブモジュールのマルチリポ構成）: 実際に作業が行われるリポジトリ（サブモジュール内での作業ならそのサブモジュール、親での作業なら親）の `docs/trial-log/` に置く。親リポジトリ直下にまとめない。
- **作成タイミング**: ブランチ開始時には作らない。**最初に記録すべき試行が発生した時点で作る**。
- **書き手**: **判定基準は Edit/Write 権限の有無**。Edit/Write を持つ実装ロール（`tdd-implementation` / `faithful-implementation`）は、試行・棄却・方針転換を**自分で追記・更新する**。読取り専用ロール（`code-review` / `adversarial-review` / `ai-antipattern-review` / `architecture` / `test-execution`）は読む義務を負い、**報告のみ**行い、メインが転記する（REJECT を出した側の棄却理由も同じ経路）。メインは報告と trial-log を突き合わせて事実確認し、前提が欠けていれば「不明（ワーカー未報告）」と書く（**推測で埋めない**）。
- **ワーカーの報告契約**は `95-orchestration-protocol.md`「ワーカー出力契約」の 5 項目（目的・前提・やったこと・結果・残課題）と、記録した trial-log ファイル・エントリのポインタ。
- **`docs/plan/` / ADR との違い**: plan は「これからやること」、ADR は「決めたこと」、trial-log は「試したことと、その過程」。plan は完了後に削除するが、trial-log は削除せず蓄積する。

**読む義務（書くだけでは再訪を防げない）**: 着手する論点に関係する trial-log ファイルが存在する時、次の読み手はそれを読む。探し方は `ls docs/trial-log/` でファイル名を一覧し、該当が無ければ「無し」として進む（コストは `ls` 1 回）。他ファイルはこの表を再掲せず参照する。

| 誰が | いつ | 何のために |
|---|---|---|
| 実装・設計を担うメイン／ワーカー | 実装・設計への着手・再開時、および同一領域へ再着手する時 | 棄却済みのアプローチを再試行しない |
| レビュー・検証ロール（`code-review` / `adversarial-review` / `ai-antipattern-review`） | レビュー・検証着手時 | 既に棄却された案を「改善提案」として再提示しない／棄却理由の妥当性を検証する |
| 調査・計画役（計画立案時の探索役 / `architecture` ロール） | 調査時（`92-plan-mode-protocol.md`） | 棄却済み選択肢を計画へ再投入しない |

この表の読み手はロールIDで明示列挙する（検査対象を確定させるため）。読み手を追加する時は `generators/check-agent-blocks.sh` の正準ブロックも更新する。

- **探し方（サブモジュール）**: 親リポジトリでセッションを開始した場合は、親の trial-log だけでなく、実際に作業する各サブモジュール内の `docs/trial-log/` も確認する（例: `ls docs/trial-log/ path/to/submodule/docs/trial-log/ 2>/dev/null`）。

- **ライフサイクル**: ブランチ完了時（**PR 作成前、またはローカルマージ実行前**）に、そのブランチで作成・更新した trial-log ファイルを見直し、**恒久価値のある試行と棄却理由を ADR の「検討した選択肢」へ昇格**させ、ADR から該当エントリへリンクする。昇格後もファイルは削除せず残置する。棚卸しと昇格の判断はメインが `git-compose` ロールへ委譲する**前に**済ませる。

## 作成原則
- **プランニング時のコードスニペット禁止**: 計画・設計段階の文書では意図・方針・インターフェースを自然言語で記述し、実装の詳細はコード本体に委ねる（二重管理・乖離を防ぐ）。例示が不可欠な場合のみ最小限の JSON 例またはフィールド表に留める。
- **アスキーアート禁止**: 図示は Mermaid 等のテキストベース作図記法を用いる。ディレクトリツリーも罫線で描かず、表または箇条書きで表現する。
- **エージェントによる作成**: `docs/adr/`・`docs/trial-log/` は規約に該当したら依頼が無くても作成・追記してよい。それ以外の文書は依頼があるとき、または依頼の遂行に必要なときに作る（作った理由を報告に書く）。
- **参照順（必要な時）**: 作業に関係する範囲だけを `README.md` ➔ `docs/prd/` ➔ `docs/design/*.md` ➔ `docs/adr/` の順で辿る（無関係な通読はしない）。

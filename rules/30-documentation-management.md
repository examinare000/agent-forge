# 30. ドキュメント管理

## ドキュメント形式ポリシー（正本の所在）🟠

本プロジェクトは **Agentic Coding** を基本とするため、ドキュメントは
**AI が理解・運用しやすいこと**と**人間にとって可読性が高いこと**の両面で最適化する。
判断軸は「**正本 vs 生成物**」と「**常時ロード vs オンデマンド**」。

> **基本原則: Markdown を単一正本とし、人間向け HTML は SSG（MkDocs）で生成する。**
> Agentic Coding のベストプラクティス（単一正本・段階的開示・低トークン）に従う。
> 背景・調査はプロジェクトの `docs/research-reports/` 配下に残す。

| 区分 | 正本（編集対象） | 役割 |
|------|------|------|
| 設計書・仕様書 | **Markdown**（`docs/design/*.md`） | AI が低トークンで読め、git 差分・レビューも軽い単一正本。図は **Mermaid**。HTML は `mkdocs build` で生成（手編集しない） |
| ADR・要件・計画・運用 | **Markdown**（`docs/adr/`・`prd/`・`plan/`・`operations/`・`tech/`） | 意思決定・現在状態の **AI コンテキスト圧縮層**。コードベース全調査を不要化する |
| 索引（段階的開示） | **Markdown**（`docs/README.md`・ルート `AGENTS.md`） | 「何を・いつ読むか」の索引。本体は必要時にオンデマンド取得 |
| 人間向け表示 | **HTML（生成物）** | `docs/design/*.md` から SSG で生成。手で編集しない。`docs/design/app-ui.html` 等の手書きビジュアル正本は例外として残置 |

- **正本は Markdown**: 設計・仕様も Markdown を唯一の正とする。HTML を手保守の正本にしない（二重管理・乖離・トークン肥大を招くため）。
- **HTML は生成物**: 人間向けの体裁は `mkdocs build` で生成する。生成物（`site/`）は編集せず、コミットもしない。
- **図は Mermaid**: 手書き SVG ではなく Mermaid（テキスト・差分追跡可）を用いる。
- **実装の正本はコード**: 設計書は責務・契約・意図の記述に徹し、実装コードは掲載しない。

## ディレクトリ構造
- `docs/README.md`: **ドキュメント索引**（段階的開示の入口）
- `docs/design/`: **設計書・仕様書の正本（Markdown）**。HTML は生成物
- `docs/prd/`: 要件定義 (PRD)
- `docs/adr/`: アーキテクチャ決定レコード (ADR)
- `docs/plan/`: 実装計画・タスク指示書（作業領域。完了後は恒久ドキュメントへ移し削除）
- `docs/trial-log/`: **試行ログ / 開発ノート**（開発中ずっと追記・更新する live-docs。目的・現在地・試したことと結果・棄却済み・残課題。ADR の補助ドキュメント）
- `docs/tech/`: 技術文書（DBスキーマ、API設計等）
- `docs/operations/`: 運用文書
- `docs/research-reports/`: 調査・評価レポート

## ドキュメント規約

### PRD
- **配置**: `docs/prd/<機能域>-<内容>.md`
- **構成案**: 概要（目的と背景） / 機能・非機能要件 / 受け入れ基準（条件・実行・結果）

### ADR
- **配置**: `docs/adr/<3桁連番>-<決定内容>.md`
- **ポリシー**: 既存ADRは変更せず、新ADRで上書き（ステータス: 採用済み / 廃止 / 検討中）
- **構成案**: 背景 / 検討した選択肢（メリット・デメリット） / 決定 / 理由 / 結果（影響）
- **trial-log との連携**: 「検討した選択肢」の各項目からは、対応する試行の詳細（何を試し何が起きたか）を `docs/trial-log/<file>` の該当エントリへリンクする。ADR は決定の要約に徹し、過程は補助ドキュメント側に置く。

### trial-log（試行ログ / 開発ノート）

**位置づけ**: 開発中ずっと追記・更新し続ける**live-docs**（作業メモ）。完成後にまとめる報告書ではない。**ADR の補助ドキュメント**であり、ADR が「どう決めたか」を1枚に要約するのに対し、trial-log は「そこへ至る過程で何を試し、何が起きたか」を保持する。
**防ぐ対象は3つ**: ①同一セッション内で同じミスを繰り返す ②コンテキストが伸びて作業の目的を見失う ③過去に試して棄却した案を再試行・再提案する。これらは**書いた瞬間ではなく読み返した瞬間に防がれる**ため、「最後にまとめて書く」運用では価値が出ない。
ただし**成功した試行の正本は ADR・設計書・コミットログ**にあるため、trial-log で成功試行を再記述しない（重複記録の禁止。1行の参照で足りる）。結果として、蓄積されるエントリは失敗・棄却が中心になる — これは運用の帰結であって、記録対象を失敗に限る規定ではない。
記録義務のトリガ（いつ書くか）は `94-self-improvement-protocol.md` が正本、**手続きと書式の詳細は Skill `trial-log`** が正本。本節は配置・単位・読む義務・ライフサイクル（ルールとしての義務）を定める。記録義務の適用優先度は 94（🟠 高）に従う。

- **配置と単位**: `docs/trial-log/<論点のスラッグ>.md`。**1 ファイル = 1 つの試行内容**（ブランチ単位ではない）。ファイル名は「何を決めようとしているか」が読み取れるスラッグにする（例: `retry-backoff-strategy.md`）。日付の前置は任意（既存ファイルの流儀に合わせる。**同じディレクトリ内で混在させない**）。追記型・新しいエントリを下へ。
  - **ブランチ単位にしない理由**: 1 ブランチで複数の関心事を試すことがあり、逆に 1 つの試行内容が複数ブランチ・複数セッションにまたがることもある。読み手は「このブランチで何をしたか」ではなく「この論点で過去に何を試したか」を探すため、内容で引ける単位にする。
  - **サブモジュール構成の場合**: 実際に作業が行われるリポジトリ（サブモジュール内での作業ならそのサブモジュール、親での作業なら親）の `docs/trial-log/` に置く。読み手はそのサブモジュール単体でも作業することがあり、当該モジュール内の過去試行にアクセスできる必要があるため、親リポジトリ直下に trial-log をまとめない。
  - **既存ファイルへの追記か新規作成か**: `ls docs/trial-log/` で同じ試行内容のファイルを探し、**あれば追記**（日付は最初の作成日のまま）、無ければ新規作成する。判定は各ファイル冒頭の**範囲の1文**に照らす — 収まるなら追記、収まらないなら新規。
    - **論点が包含関係にある時**（例: 「API のエラー処理」と「リトライ戦略」）は、**広い方の既存ファイルへ追記**する。狭い論点で新規ファイルを作ると、後から読む側が両方を見つけられない。広いファイルが1画面で追えない規模に育った時点で、狭い論点を切り出して元ファイルからリンクする。
    - **命名は判断軸で行う**（何を決めようとしたか）。実装対象やファイル名で名付けない — 同じ実装対象について別の判断軸で試すことがあり、名前が衝突する。
    - 迷ったら追記を選ぶ。**乱立より肥大の方が回復しやすい**（分割は後からできるが、散ったファイルの発見漏れは検知できない）。
  - **ファイル冒頭**: 1行目に `# trial-log: <試行内容>`、2〜3行目に**この論点の範囲を1文**（どこまでを扱い、何を扱わないか）、続けて関連するブランチ・PR・ADR を任意で記す（関連付けであって単位ではない）。範囲の1文は、近い論点のファイルが乱立した時の振り分け基準になる。
- **作成タイミング**: ブランチ開始時には作らない。**最初に記録すべき試行が発生した時点で作る**（空ファイルのノイズを防ぐ）。
- **書き手**: Write/Edit 権限を持つワーカー（`tdd-strict-coder` / `implementation-coder` / `code-reviewer` / `ai-antipattern-reviewer` / `adversarial-verifier` 等のレビュアー、および `testability-architect`）は、作業中に発生した試行・棄却・方針転換を**自分で追記・更新する**（試行を1つ終えたその場・アプローチ切り替え時・REJECT 判定を出した/受けた時）。読み取り専用ワーカー（planner / explorer / test-runner 等 Write を持たない・またはコード変更を伴わないエージェント）は従来どおり報告のみ行い、必要ならメインが転記する。オーケストレーター（メイン）は、ワーカーが書いたエントリを完了報告と突き合わせて事実確認し、誤り・書式逸脱・重複を修正・統合する。
- **形式**: 詳細は Skill `trial-log` が正本（節構成・追記トリガ・書き方）。ルールとして最低限満たすべき要件は次の4点。
  - **冒頭で「目的」と「現在地」が読める**こと。この2つは追記ではなく**上書きで最新に保つ** — 目的の見失いを防ぐ一次手段はここを読み直すことなので、古い記述が残っていると機能しない。
  - **棄却した案が独立して引ける**こと（節を分ける）。再提案の抑止に使うため、成否が混在した本文に埋めない。
  - **観測と推測を区別する**こと（推測には「推測:」を付ける）。「効かなかった」で終わらせず、なぜそうなったかの観測を書く（原因不明なら「原因未特定」と明記）。
  - **根拠の指し方**: ルール・規約文書は行番号ではなく `path` + 節見出しで指す（行番号は後続の編集でずれる）。コードは `path:line` に関数名・クラス名を併記する（試行錯誤中は行がずれる）。実装コードは貼らない。エラー抜粋は再現に必要な最小限。秘密情報（トークン・鍵・個人情報）を書かない（`12-security-guidelines.md`）。
- **ワーカーの報告契約は5項目のまま**（目的・前提・やったこと・結果・残課題）。加えて、完了報告には「記録した trial-log ファイルとエントリ」のポインタを含める（例: `docs/trial-log/api-retry-strategy.md#1220-retry-backoff` 等。新規ファイル作成時は新規作成の旨を明記）。ファイルの節構成と報告の項目は別物であり、メインは必要に応じ受け取った5項目を上記の節へ振り分けて統合する。
- **オーケストレーターによる修正・統合**: ワーカーの報告に**前提**が含まれていない場合、メインは自分が把握している範囲で補い、補えなければ「不明（ワーカー未報告）」と書く。**推測で埋めない**（捏造した前提は後続の判断を誤らせる）。ワーカーが複数いて同一論点に触れた場合、追記中心の運用とメインの統合で衝突を吸収する。同じ欠落が繰り返すならブリーフの不備として CLAUDE.core.md の出力契約を見直す。
- **1行参照の書式**（成功試行で ADR・設計書・コミットログに正本がある場合。詳細は `94-self-improvement-protocol.md`「成功した試行の扱い」）: `## <HH:MM> <要約> — 正本: <docs/adr/xxx.md 等 or コミットハッシュ>` の1行のみ。この形態では5項目を要求しない。
- **記述原則**:
  - 「効かなかった」で終わらせない。**なぜそうなったか**の観測を必ず書く（原因不明なら「原因未特定」と明記する）。
  - 実装コードは貼らない（本ファイルの「作成原則」に従い、アプローチと契約の記述に留める）。エラー抜粋は再現に必要な最小限。
  - 秘密情報（トークン・鍵・個人情報）を貼らない（`12-security-guidelines.md`）。
- **`docs/plan/` / ADR との違い**: plan は「これからやること」、ADR は「決めたこと」、trial-log は「試したことと、その過程」。plan は完了後に削除するが、trial-log は削除せず蓄積する。

**読む義務（書くだけでは再訪を防げない）**: ワーカーが自分で記録し、メインが事実確認・修正判断を行う体制のため、読み手は複数に義務付ける。

| 誰が | いつ | 何のために |
|---|---|---|
| 実装を担うメイン／ワーカー | 作業開始・再開時、および同一領域へ再着手する時 | 棄却済みのアプローチを再試行しない |
| レビュアー・検証役（`code-reviewer` / `adversarial-verifier` / `ai-antipattern-reviewer`。上位互換を使う場合も同じ） | レビュー・検証着手時（関連する試行内容のファイルが存在する場合） | 既に棄却された案を「改善提案」として再提示しない／棄却理由の妥当性そのものを検証する |

**探し方**: `ls docs/trial-log/` でファイル名（＝試行内容）を一覧し、着手する論点に関係するものを読む。該当が無ければ「無し」として進めてよい（存在確認のコストは `ls` 1回）。
  - **サブモジュール構成のリポジトリでセッションを親で開始した場合**（例: 親リポジトリで作業開始し、後にサブモジュール内へ進む、または複数サブモジュール間での作業）は、親リポジトリの trial-log だけでなく、実際に作業する各サブモジュール内の `docs/trial-log/` も確認する（例: `ls docs/trial-log/ path/to/submodule/docs/trial-log/ 2>/dev/null`）。親の視界からはサブモジュール内のファイルが見えず、読み忘れが起きやすいため。

- **ライフサイクル**: ブランチ完了時（**PR 作成前、またはローカルマージ実行前**の棚卸し）に、そのブランチで作成・更新した trial-log ファイルを見直し、**恒久価値のある試行と棄却理由を ADR の「検討した選択肢」へ昇格**させ、ADR から該当エントリへリンクする。昇格後もファイルは削除せず残置する（レビューと次セッションの参照資産のため）。棚卸しと昇格の判断はメイン（オーケストレーター）が PR / マージを `git-composer` へ委譲する**前に**済ませる（git-composer に恒久価値の判断をさせない）。

## 運用＆ライフサイクル

### 更新タイミング
- 設計書・仕様書（HTML 正本）: 仕様・設計の確定変更時に同期
- PRD: 要件変更時に即座
- ADR: 技術決定時に新規作成
- trial-log: 記録すべき試行を1つ終えたその場で追記（後回しにするとエラー実文と観測が失われる）
- 技術文書・運用文書: 実装/運用変更時に即座に同期

### 品質基準
- 対象読者の明確化、日本語記述、最終更新日の記載。

### 作成原則
- **プランニング時のコードスニペット禁止**: 計画・設計段階の文書では過度なコードスニペットを記載しない。意図・方針・インターフェースを自然言語で記述し、実装の詳細はコード本体に委ねる（コードと文書の二重管理・乖離を防ぐため）。例示が不可欠な場合のみ最小限に留める。
- **アスキーアート禁止**: 図示が必要な場合はアスキーアート（ASCII art）を使わず、Mermaid 等のテキストベース作図記法を用いる（保守性・可読性・差分追跡性のため）。ファイル構成・ディレクトリツリーも罫線（`├──` 等）で描かず、表または箇条書きで表現する。
- **設計書（HTML 含む）も同原則を適用**: `docs/design/` 配下の設計書（`*.html` のビジュアル設計書を含む）も上記 2 原則に従う。実装コード（クラス本体・関数実装・設定ファイル中身等）は掲載せず、責務・インターフェース・データ契約は自然言語・表・Mermaid／SVG で示す。API リクエスト/レスポンスや DB スキーマなど例示が不可欠な場合は、最小限の JSON 例またはフィールド表（項目・型・説明）に留める。実装の正本はコード、設計書は意図と契約の記述に徹する。

### エージェント行動指針
- **作成**: 明示的要求時のみ適切なテンプレートに従い作成。**例外は trial-log**（`94-self-improvement-protocol.md` のトリガ該当時は依頼が無くても自発的に作成・追記する）。
- **参照**: 正確なパスで参照し、関連ドキュメントとの整合性を検証。
- **更新**: 影響範囲のドキュメントを同時に更新し、変更理由を明記。

### メンテナンス＆オンボーディング
- **確認**: 月次（乖離チェック）、四半期（体系見直し）、リリース前（更新確認）。
- **推奨読順**: `README.md` ➔ `docs/prd/` ➔ `docs/design/*.html`（設計・仕様の正本） ➔ `docs/adr/`

# 資料: 委譲経路の実体とタイブレーク詳細（`95-orchestration-protocol.md` の補足。provider 固有・現行環境の対応表）

## 委譲経路の実体（Claude をメインとする環境）
- **別ベンダーの実装役**（選定表 行3）: `codex:codex-rescue`（`/codex:rescue`）。純粋なフォワーダ — Codex を実行するが検証もコミットもしない。戻ったらオーケストレーターがゲートを所有する: `test-execution` ロールで検証 → 差分レビュー → `git-compose` ロールでコミット。Codex 主導のコードレビューは `/codex:review`。
  - **model は指定しない**（単一更新点。ユーザーが明示した時のみ `--model`）。**effort はロール駆動で明示する**（下限は `02-model-fallback-matrix.md`「Codex 側のモデル解決」）。`codex-rescue` を必須ゲートの起動経路にはしない。
  - **ブリーフは operator 式で書く**: 1 run 1 タスク、done の定義を明示、read-only は task text に明記する（フラグではなくフォワーダの判断で `--write` が付くため）。reasoning を上げる代わりに検証ループと出力契約をブリーフに書く。詳細はプラグイン同梱の `gpt-5-4-prompting` スキル。
- **大コンテキスト委譲役**（行4）: 導入環境に当該 provider があれば、その大コンテキスト委譲機構（無ければ `.mcp.json` の対応 MCP）。
- 当該 provider をメインとする環境では、その環境の固有指示が実体を持つ。

## Codex native の起動と役割境界

- Main は全体判断と分解を担当し、SubAgent には独立して検証できる小さな仕事を渡す。モデル・effort の許可範囲は `02-model-fallback-matrix.md`「Codex 側のモデル解決」の解決規則に従い、役割は以下の一般表で選ぶ。既定 agent への無指定起動で Main の設定を継承させず、profile を持つ役割を選ぶ。
- `collaboration.spawn_agent` を使う環境では、独立レビューを `fork_turns="none"` で起動する。実装・調査も自己完結ブリーフで足りる場合は履歴を継承しない。利用機構に同等の選択肢がなければ、別の新規セッションで独立文脈を確保し、その方法を報告する。
- custom agent の model / effort は起動時指定より優先するため、役割の設定と異なる値を指定しただけで変更済みと主張しない。変更後の実効値は新規セッションで確認する。
- Codex への native 委譲を通常の経路とする。MCP 中継は利用可能なツールを確認し、固定された ToolSearch・Read・Edit 等の名前を前提にしない。
- 停止した agent への回答・追加情報は同じ agent へ送る。現在の機構なら稼働中は `send_message`、終了後の継続は `followup_task` を使う。native agent を一律に非対話と扱わない。
- reviewer の read-only は編集しないという役割規律であり、カスタム agent ファイルの `sandbox_mode` は親の権限を上書きしない。技術的な書込禁止が必要な作業は、親の権限設定で成立する環境から起動する。既存の sandbox・承認・フックを維持する。
- 指定コマンドを実行する agent は終了コードとログを報告し、テストの十分性・品質・マージ可否を判定しない。build/cache 等の通常の生成物と、ソースの修正を区別する。

仕様の根拠: [OpenAI Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)（2026-10-16確認）。

## タイブレーク詳細
- **大コンテキスト読解 vs リポ内探索**: **単一ファイルが数千行超・対象が数十ファイル規模・出力が巨大なログ**なら大コンテキスト委譲役。**所在特定や数ファイルの確認で足りる**なら探索役。迷ったら探索役を先に投げ、「大きすぎて要約しきれない」と返ってきた時点で切り替える（切り替えたら (t4) として記録）。
- **忠実実装 vs TDD 実装**: 要件と受入条件が確定済みなら忠実実装役、原因調査・振る舞いの解明が必要なら TDD 実装役。両者とも振る舞いの変更には TDD を適用する。Codex native では既存契約内の可逆な局所判断は許可し、範囲を超える判断は該当箇所を未変更で Main へ返す。
- **第2実装 vs 競合提案**: 実装を進めたいなら別ベンダーの実装役へ単独委譲、方針が未確定なら先に競合提案。

## ターン予算と粒度（実測）
- 予算不足を「続行」の往復で埋めると、粒度を変えないまま同じ停止を繰り返す。`maxTurns` の引き上げは粒度の代替にならず、コンテキスト予算の検査と整合を要するためユーザー判断。
- 調査・レビュー系ブリーフで「関連箇所を探す」を委ねると読みで予算を使い切る。件数計測は heredoc 1 本のスクリプトとして渡す。書き始めの期限は絶対ターン数で書き、期限到達時の再開指示は「これ以上読まず、手持ちの観測だけで書く」を含める（2026-09-13 適用後も、読む対象が非有界なブリーフでは 3 セッションで再発した）。
- オーケストレータは自分が書くブリーフ・報告の引用にも範囲検査（行番号 ≤ 行数・逐語一致）を課す。複数ファイルを連結した出力（`cat a b`）の行番号は引用に使わない。
